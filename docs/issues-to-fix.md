## Not done, needed before launch

The owner's order: finish the product first; the last three steps below come
last, each only on the owner's yes.

- [ ] **A sites domain of our own on the Public Suffix List** (audit 2026-10-22, finding #1). Not possible on dpdns: the list needs 2+ years of registration, and dpdns renews yearly. Until then (decided 2026-10-28, sign-ups still closed): built 2026-10-29, the gateway keeps server-rendered sites' cookies their own (ADR 0011: `Domain=` stripped, `HttpOnly` cookies stored as `__Host-`, planted copies dropped and deleted, sibling sites' requests treated as cross-site); what stays open is eviction and flooding, password managers, blocklists, and cookies sites' own scripts set. Before opening sign-ups, Google Search Console on `autodeploy.dpdns.org` to hear of any flag the same day (owner's Google account and one DNS record). User sites live on `autodeploy.dpdns.org`, apart from the dashboard (dpdns.org is on the list, so browsers and Safe Browsing treat it separately from autodeploy.fyi). But every user site shares that one entry, so one site can set cookies for another and one phishing site can get every user site flagged. Vercel's fix: `vercel.app` is itself on the list. Ours: buy a sites domain for 2+ years (the list requires it; free dpdns renews yearly) and submit it; approval takes weeks, browsers pick it up over months. Checked 2026-10-29 against the list's guidelines: the expiry must be more than 2 years past the request's date (autodeploy.fyi expires 2027-10-21, so one more year isn't enough), and projects "not serving more then thousands of users are quite likely to be declined", so apply only once sign-ups are open and used. There's no promised review time. Listing `autodeploy.fyi` itself would make `app.` and `api.` separate sites, and the dashboard's sign-in (Lax cookies on `api.`, called from `app.`) would stop working until the API is served from the dashboard's address; a separate sites domain avoids that. How others managed before (checked 2026-10-29): Vercel (`now.sh`, 2016) and Netlify (2017) were listed while small, when the list took small projects; Railway ran unlisted from 2020 until August 2025; a small deploy platform (`deployzy.app`) was declined in August 2026 for its user count. GitHub, before moving Pages to `github.io` (2013), dropped duplicate session cookies across every path prefix and caught escaped names, and moved because cookie overflow beat that. `__Host-` cookies, which came later, close that hole, so our edge plan is GitHub's plus `__Host-`.

**2026-10-24**
- [x] **Next.js sites wake in 1.7-2.8 s** (gateway; 4.4-7.8 s that morning): bundles left unpacked by the build, and a site may use a whole CPU when it's spare (`RUNTIME_CPUS` 1, weight 512, below the platform's 1024). The Node server wakes in ~0.5 s.
- [x] **CPU split (90/10):** sites and builds together get at most 90% of the VM's CPUs, so the platform always keeps 10%; sites alone at most 75%, so a build always keeps some (it took 676 s instead of 71 s with 20 sites busy). systemd slices made by `ship.sh`; a site, build or check that Docker won't start in its group starts without it rather than not at all. Measured: a build with the sites group saturated took 227 s (676 s before the split, ~71 s alone), getting a fixed third of the sites-and-builds CPU however many sites are busy; the API stayed fast throughout.
- [x] **Incident: every user site down (500, Cloudflare 1101) from ~09:35 UTC, caused by our own load test.** The edge Worker read Workers KV on every visit; the two capacity tests (~260,000 visits) used up KV's free 100,000 reads for the day, after which every KV read failed and the Worker threw on every request. Fix: the edge keeps each address's answer in the free, unlimited edge cache for 30 s (KV reads drop from one per visit to about one per address per 30 s per Cloudflare location), and when KV fails it asks the origin (`/internal/routes`, from the database, now honouring takedowns and suspensions). Lesson: load tests through the edge must stay well under Cloudflare's free daily limits (Workers 100,000 requests, KV 100,000 reads), or go around the edge.
- [x] **Faster first wake after a deploy:** the build now leaves the site's server bundle unpacked where the gateway runs sites from, instead of the first visitor waiting for it to be fetched and unpacked (~4 s of a 7.8 s Next.js wake in the capacity test); the gateway also notices a started site is ready sooner (every 100 ms, was ~400 ms) and logs where each wake's time went.
- [x] **Old unpacked bundles are deleted:** 67 had piled up (2.5 GB) because nothing ever removed them. Hourly, the gateway deletes those not running, not live and unused for 24 hours; they're still in storage if needed again.
- [x] **Deleting a project stops its awake sites** within 30 seconds, instead of leaving them running until idle; the gateway's stop for a deleted site no longer fails, and one failure can't hold up the others.
- [x] **Capacity test on the VM** (report: `AutoDeploy-capacity-test-2026-10-24.docx`): 20 real server-rendered sites (10 Next.js, 10 Node) woken in steps of 5 through their public addresses, every awake site loaded at each step, a build run with 20 awake, then a 21st woken. 20 awake used ~1.1 GiB (~57 MiB each); free memory never below 7.4 GiB. CPU is the limit when many sites are busy at once: total throughput levels off at ~150-160 pages a second, and median response time went 78 → 247 ms from 5 to 20 busy sites; idle awake sites cost ~0 CPU. Every one of ~15,000 requests answered 200. The 21st put the longest-idle site to sleep, which woke again on its next visit. `RUNTIME_MAX_AWAKE` stays 20.
- [x] **Server-rendered sites only wake into memory the VM has:** "20 awake at once" was never measured, and at full caps it needs ~15.5 GB of a 12 GB VM. If memory falls below 2 GB later (a build started), idle sites sleep until it recovers. Out of memory, Linux could have killed Postgres and taken everything down; now a site sleeps instead (ADR 0008 amendment).
